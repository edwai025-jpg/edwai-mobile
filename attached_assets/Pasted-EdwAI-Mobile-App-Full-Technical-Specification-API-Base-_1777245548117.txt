Token Management

Every API response that logs the user in returns:

{
  "access_token": "eyJ...",          ← JWT, store in memory / secure storage
  "refresh_token": "raw-string",     ← Long-lived, store in Keychain/Keystore
  "token_type": "bearer",
  "is_new_user": true | false,
  "profile_complete": true | false,
  "user": { ...user object... }
}

Access token goes on every authenticated request as a header:

Authorization: Bearer {access_token}

Refresh token is used to silently get a new access token when any call returns 401:

POST /api/auth/token/refresh
Body: { "refresh_token": "{stored_refresh_token}" }
Response: { "access_token": "eyJ...", "token_type": "bearer", "user": {...} }

Navigation rule after login:

if user.profile_complete == true  → go to Home/Dashboard screen
if user.profile_complete == false → go to Complete Profile screen

Screen 1 — Login

Three tabs / methods shown on one screen. Default is Phone tab.
Method A: Phone OTP (India only, +91)

Step 1 — Enter phone number

UI: A "+91" prefix label + 10-digit numeric input field
Validation before calling API:
  - Exactly 10 digits
  - Starts with 6, 7, 8, or 9
  - Strip all non-digits from input
POST /api/auth/phone/send-otp
Body: { "phone": "+91{10digits}" }
  e.g. { "phone": "+918876543210" }
Success: show OTP entry screen, start 60-second countdown
Error: show detail field from response body

Step 2 — Enter OTP

UI: 6 individual digit boxes (like a PIN entry)
    "OTP sent to +91 {phone}" subtitle
    "Resend" link (disabled until 60s countdown expires)
    "Change number" link → go back to Step 1
POST /api/auth/phone/verify-otp
Body: { "phone": "+91{10digits}", "otp": "123456" }
Success Response:
  { access_token, refresh_token, token_type, is_new_user, profile_complete, user }
  → Store tokens → navigate based on profile_complete flag
Error 400: "Invalid or expired OTP" → show error, let user retry or resend

Method B: Email OTP

Step 1 — Enter email

UI: Standard email text input
Validation (client-side before API call):
  - Not empty
  - Length 5–254 characters
  - Exactly one @ symbol
  - Part before @ doesn't start/end with dot, no consecutive dots
  - Domain has at least one dot
  - TLD at least 2 characters
POST /api/auth/email/send-otp
Body: { "email": "student@example.com" }
Success: show OTP entry screen, start 60-second countdown
Error: show detail from response

Step 2 — Enter OTP

UI: Same 6-box PIN entry as phone
    "OTP sent to {email}" subtitle
    "Change email" / "Resend" links
POST /api/auth/email/verify-otp
Body: { "email": "student@example.com", "otp": "123456" }
Same success/error handling as phone OTP verify.

Method C: Google Sign-In (OAuth via in-app browser)

The backend runs a standard OAuth 2.0 Authorization Code flow. On mobile:

Flow:

    Open an in-app browser (iOS: ASWebAuthenticationSession; Android: Chrome Custom Tabs) pointing to:

    GET https://edwai-api-953672603784.asia-south1.run.app/api/auth/google

    Google shows its sign-in screen in the browser
    After sign-in, Google calls the backend callback, which then redirects the browser to one of:

    https://edwai-prod-70474.web.app/complete-profile?token={jwt}
    https://edwai-prod-70474.web.app/student?token={jwt}

    Your in-app browser must intercept this redirect and extract the token query parameter

Implementation note: Configure the in-app browser session to watch for URLs starting with https://edwai-prod-70474.web.app and intercept them. When intercepted:

    Parse ?token= from the URL → this is the access token
    Parse the path (/complete-profile vs /student) to know where to navigate
    Important: After Google OAuth you only get an access token in the URL, not a refresh token. Immediately call POST /api/auth/token/refresh is not applicable here; instead, call GET /api/auth/me with the token to fetch the full user object, then store the token

Alternative approach (recommended for mobile): If you're using a Google Sign-In SDK (Google Identity iOS SDK / Google Sign-In for Android), you can get the Google ID token client-side and exchange it with the backend. However, the current backend does not have this endpoint — it only supports the browser redirect flow. Use the in-app browser approach above.

Save Profile API

Called by every "Continue" button variant:

PATCH /api/auth/me/profile
Headers: Authorization: Bearer {access_token}
Body: {
  "full_name": "Rahul Sharma",        ← required
  "state_id": 1,                      ← nullable int
  "board_id": 5,                      ← required int
  "class_id": 12,                     ← optional int (only if class selected)
  "phone": "+918876543210"            ← optional, only if entered
}
Success Response:
{
  "success": true,
  "profile_complete": true,
  "user": { ...full user object... }
}
→ On success: navigate to Home/Dashboard screen
→ On error: show detail from response as error banner

Validation before calling:

    full_name must not be empty
    board_id must be set
    Terms checkbox must be checked
    If phone entered: must be 10 digits, must start with 6/7/8/9

User Object Shape

Every auth response returns a user object:

{
  "id": 42,
  "email": "student@example.com",
  "phone": "+918876543210",
  "full_name": "Rahul Sharma",
  "state": "Maharashtra",
  "state_id": 7,
  "board": "CBSE",
  "board_id": 5,
  "class_id": 12,
  "class_name": "Class 10",
  "medium_id": null,
  "medium_name": null,
  "is_admin": false,
  "role": "student",
  "auth_provider": "phone",     ← "phone", "email", or "google"
  "phone_verified": true,
  "email_verified": false,
  "profile_complete": true,
  "google_id": false,
  "profile_photo_url": null
}

Logout

POST /api/auth/logout
Headers: Authorization: Bearer {access_token}
Body: { "refresh_token": "{stored_refresh_token}" }
→ Clear stored tokens, navigate to Login screen
