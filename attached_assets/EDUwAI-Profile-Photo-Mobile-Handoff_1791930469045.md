# EDUwAI Mobile Handoff: Profile Photo

## 1. Scope and key integration rules

This is a standalone addendum to the Education & Account handoff. It covers the highlighted My Profile header avatar, Change Photo, the crop dialog, uploading/replacing, displaying, and removing a profile photo.

Based on current workspace source and the supplied highlighted reference image. No web/backend changes, actual uploads, account changes, or deletions were performed. Production availability and native device behavior were not live-tested.

- Reuse the existing EDUwAI backend and authenticated mobile session.
- Upload and replacement are the SAME POST operation. There is no separate photo PUT/PATCH or crop API.
- There is no OTP, Education Save, or Account Save requirement. Successful POST/DELETE commits immediately.
- All three photo endpoints are authenticated and act on the current user from the bearer token. Do not send a target user ID.
- The returned `profile_photo_url` is a logical storage key, NOT a public/signed download URL.
- Read the image through the authenticated GET endpoint. Do not construct a public bucket URL.
- Crop/selection happens client-side. Use the mobile application's existing image-picker/crop/image components, not browser DOM/canvas code.
- The image shown by the UI is circular, but the saved image is a square/rectangular JPEG, not a transparent circular PNG.

## 2. API base, authentication, and index

Configured non-development origin in the web source:

```text
https://api.eduwai.in
```

This is configuration found in source, not confirmation that production was contacted. If the mobile client's base already ends in `/api`, append `/student/profile/photo`, not `/api/student/profile/photo`.

| Operation | Method and path | Request | Success |
|---|---|---|---|
| Initial upload | POST /api/student/profile/photo | Multipart file field named file | JSON success + storage key |
| Replace/update | POST /api/student/profile/photo | Same multipart request | Same storage location overwritten |
| Display/read | GET /api/student/profile/photo | No body | Binary image/jpeg |
| Remove | DELETE /api/student/profile/photo | No body | JSON success |
| Refresh saved user | GET /api/auth/me | No body | User object with profile_photo_url |

Protected requests use:

```text
Authorization: Bearer <existing access token>
```

Use the existing mobile session client's refresh/retry handling. The web API transport attaches credentials/bearer headers and refreshes an expired access token once; browser cookies are not automatically available to native network libraries. No storage-service/provider credential belongs in the mobile app.

Photo handlers have no additional institution/student-role check beyond current-user authentication. Their student path/name must not be treated as proof of an extra role guard.

## 3. POST: upload and replacement

```http
POST /api/student/profile/photo
Authorization: Bearer <existing access token>
Content-Type: multipart/form-data; boundary=<generated by networking library>
```

Multipart contract:

| Field | Required | Type and example |
|---|---|---|
| file | Yes | Binary image part; filename photo.jpg; part MIME image/jpeg |

Do not send JSON/base64, `photo`, `image`, `profile_photo_url`, crop coordinates, or `user_id` in place of the required binary `file` part.

The multipart library should generate the boundary. Do not set the whole request to `image/jpeg` or a boundary-less multipart Content-Type. The FILE PART carries `image/jpeg`; the REQUEST carries multipart/form-data.

### Accepted types and exact input limit

- Allowed file-part MIME types: `image/jpeg`, `image/png`, `image/webp`.
- MIME comparison is lowercased; extension alone is not sufficient.
- JPEG aliases such as `image/jpg`, HEIC/HEIF, GIF, SVG, and generic `application/octet-stream` are not in the accepted MIME set.
- Maximum submitted file bytes: **5,242,880** (5 × 1024 × 1024). Only a value GREATER than this is rejected by the explicit byte-count check.
- This limit applies to the actual uploaded/cropped file, not necessarily the original gallery file.
- A permitted MIME type with corrupt/empty/non-image data still fails decoding.
- The handler reads the file before applying its size check; it is not a presigned/direct-to-storage upload flow.

### Server processing

1. Requires the existing storage service.
2. Validates MIME and reads/checks the file.
3. Opens/decodes the image through Pillow.
4. RGBA is flattened onto white; other non-RGB modes are converted to RGB.
5. Preserves aspect ratio, shrinking within **512 × 512** if either dimension is larger. Smaller images are not explicitly enlarged.
6. Tries optimized JPEG quality 85, 75, 65, 55, then 45 until output is at most **307,200 bytes** (300 × 1024).
7. If needed, shrinks within **256 × 256** and tries JPEG quality 45.
8. If still too large, fails with the generic image-processing error below.
9. Uploads JPEG bytes to the stable logical key `profiles/{current_user.id}/avatar.jpg`.
10. Sets the current user's `profile_photo_url` to that logical key and commits if the DB lookup finds the user.

The backend performs resize/compression, not an enforced square/circular crop. It does not explicitly transpose EXIF orientation in this helper; native selection/cropping should emit correctly oriented pixels.

### Success response

```json
{
  "success": true,
  "profile_photo_url": "profiles/42/avatar.jpg"
}
```

The numeric ID here is fictional. The actual ID comes from authentication. This is not a full user object and does not issue new login tokens.

Initial upload and later replacement return the same stable key. A non-changing key does NOT mean the photo bytes were unchanged. Replacement overwrites the prior object; no previous-photo history/rollback endpoint is provided.

### Errors

| Status | detail / meaning |
|---|---|
| 401 | Missing/invalid authentication through shared auth dependency |
| 400 | Unsupported file type. Upload a JPG, PNG, or WebP image. |
| 400 | File too large. Maximum size is 5 MB. |
| 400 | Could not process image. Please use a valid JPG, PNG, or WebP file. |
| 422 | Missing file part or malformed request, using FastAPI detail array |
| 500 | Storage unavailable |
| 500 | Image processing unavailable |
| 500 | Photo upload failed. Please try again. |

Uncaught DB or infrastructure errors can also be 5xx; the table lists explicit handler responses, not a guarantee that every possible exception uses one of these messages.

## 4. GET: authenticated image display

```http
GET /api/student/profile/photo
Authorization: Bearer <existing access token>
```

Success returns a streaming **binary JPEG** with media type `image/jpeg`. It is NOT JSON, a redirect, a base64 value, or a public/signed URL.

The handler reads the current user's stored key, downloads the bytes using the existing storage service/environment prefix, and streams them.

| Status | Explicit detail / meaning |
|---|---|
| 401 | Missing/invalid authentication |
| 404 | Storage unavailable |
| 404 | No profile photo |
| 404 | Photo not found |

`No profile photo` covers a missing user lookup or missing/empty saved key. `Photo not found` covers storage download exceptions or empty bytes. A 404 therefore does not uniquely identify voluntary removal.

No separate custom photo-download URL endpoint, user-ID parameter, photo history route, or pagination exists in this path.

### Meaning of profile_photo_url

The user from `GET /api/auth/me` includes:

```json
{
  "id": 42,
  "profile_photo_url": "profiles/42/avatar.jpg"
}
```

This is an abbreviated example; `/api/auth/me` returns the user directly, not `{ "user": ... }`. After deletion its `profile_photo_url` is `null`.

Use this field to decide whether a photo exists/Remove is offered. Use authenticated GET for image bytes, not `Image(source = profile_photo_url)` as an HTTP URL.

### Native display choices

Use the existing mobile stack's authenticated image loader, or download with bearer auth and store/display an app-private temporary file. An image widget receiving only a URL without the bearer token may fail.

Scope cache identity to the signed-in user AND a local photo revision. Stable storage key alone is not enough for replacement invalidation.

After successful POST: invalidate prior cached image, update/refresh saved user, then perform a fresh authenticated GET. A local revision query such as `?v=<revision>` can serve as a client cache key if supported by the existing loader; it is not a new server API contract or versioned asset.

After DELETE/logout/user switch: remove the app's old in-memory/private-file image reference and show the appropriate current-user initial. Do not reuse another account's private avatar cache.

The photo handler adds no explicit application-level Cache-Control/ETag policy. Do not assume the backend's stable URL automatically invalidates native caches.

## 5. DELETE: remove photo

```http
DELETE /api/student/profile/photo
Authorization: Bearer <existing access token>
```

No request body, no OTP, no current storage key, and no user ID required.

Success:

```json
{"success": true}
```

Server behavior:

1. Looks up the current user; if absent returns 404 `User not found`.
2. If a saved key and storage service exist, attempts to delete the stored object.
3. Swallows exceptions from that storage delete.
4. Sets `profile_photo_url` to `null` and commits.
5. Returns success. Repeating DELETE while no photo is set still succeeds for an existing authenticated user.

Missing/invalid auth returns 401. Uncaught database errors may be 5xx.

**Important limitation:** Successful removal guarantees the user record's photo reference was cleared after commit, NOT that physical object deletion was verified. The storage method returns a boolean that this handler does not inspect, and the handler continues when storage is unavailable or deletion fails. Do not promise guaranteed physical erasure from this response.

This is photo deletion, NOT `DELETE /api/student/profile` (whole-account deletion).

## 6. Existing header UI and state

The highlighted control is shared across all My Profile tabs; it is not part of an Education field.

| Element | Existing presentation and behavior |
|---|---|
| Header avatar | 64 × 64 CSS-pixel circle; overflow hidden; purple ring; photo uses object-cover |
| Fallback | First character of full_name uppercased, or S; white bold initial; purple/indigo gradient |
| Avatar action | Title Change photo; clicking opens hidden file picker unless uploading |
| Hover overlay | Half-transparent black circular overlay; camera icon; spinner during upload, but overlay visibility is hover-driven |
| Main heading | My Profile |
| Subtitle | Manage your account settings |
| Action | Camera icon + Change Photo; purple text; becomes Uploading… and disabled during upload/removal |
| Remove | Red text; shown only if saved user.profile_photo_url is truthy; disabled while busy |
| File input | Hidden; JPEG/PNG/WebP accept list; single file, no explicit capture/camera mode |
| Compact page-header avatar | Same loaded photo/fallback initial; separate 32 × 32 circular presentation |

Remove immediately calls DELETE; there is **no separate photo-delete confirmation** in the current UI. Do not describe the Account Danger Zone confirmation as part of photo removal.

Relevant state:

| State/ref | Meaning |
|---|---|
| photoUploading | Shared upload/remove busy state |
| photoTimestamp | Local reload revision, initialized and bumped with Date.now |
| photoObjectUrl | Display URL created from authenticated GET blob |
| photoUrlRef | Previous display object URL, revoked on successful replacement or no saved key |
| cropImageSrc | Local selected-file URL; nonempty opens crop modal |
| cropImageSrcRef | Crop URL reference for revocation |
| photoInputRef | Hidden picker control |

The effect loads the image when the saved key or photoTimestamp changes. GET failure silently shows the initial by setting photoObjectUrl to null; it does not automatically clear the server key, so Remove may remain visible.

On picker selection, the first file is used, an existing crop URL is revoked, the selected file becomes a local object URL, and the input value is cleared so the same file can be selected again. Choosing no file does nothing.

The browser picker/selection handler does not explicitly check size/type before crop; the accept list guides selection, and the backend validates the submitted result.

## 7. Crop dialog and exact action sequences

### Crop UI

- Dialog title: **Crop Photo**.
- Instruction: **Drag to reposition · Scroll or pinch to zoom**.
- Centered, max-width-lg panel above the profile modal; dark/white theme; black 70% backdrop and blur.
- Crop area: height 320 CSS pixels, dark background.
- Crop aspect: **1:1**; round preview; no grid.
- Initial crop position `{x: 0, y: 0}` and zoom `1`.
- Zoom slider: min `1`, max `3`, step `0.01`.
- Top close icon with accessible label **Cancel**, plus bottom **Cancel** button.
- Primary button **Save Photo**, spinner and **Uploading…** while confirming.
- Both cancel controls and primary save disabled while confirming. Save is not separately disabled merely because cropped pixels are absent; its handler returns early in that case.
- Browser implementation uses react-easy-crop and canvas; those are implementation references, not a required native dependency.
- Crop export draws the selected pixel rectangle into a canvas of those dimensions and outputs JPEG at quality **0.92**.
- Round preview does not mask the exported bitmap to a transparent circle.
- No camera-specific UI, rotation controls, gallery history, or backdrop/Escape cancellation handler is provided in this crop block.

### Upload/replace sequence

1. Click avatar/Change Photo → native-equivalent selection.
2. File selected → show crop. There has been no server mutation yet.
3. Cancel crop → discard temporary image; existing saved photo remains.
4. Save Photo → convert cropped pixels to JPEG.
5. Set shared upload busy state and submit multipart `file`, filename `photo.jpg`.
6. On POST success: close/revoke crop URL; bump photoTimestamp; refresh authoritative user with `/api/auth/me`; show **Profile photo updated!**
7. The photo effect loads a new authenticated JPEG; same stable storage key is allowed.
8. On POST failure: show server detail or **Failed to upload photo**; keep the crop dialog/image available for retry; clear busy state.

The crop confirm handler itself uses try/finally, not a dedicated catch for local image/canvas conversion errors. A native implementation should handle picker/crop encoding failures as client errors without inventing backend error responses.

### Removal sequence

1. Click Remove → set shared busy state.
2. Send DELETE immediately; no confirmation.
3. On success: bump revision; refresh user; show **Profile photo removed**.
4. Refreshed null key causes display URL to be cleared and initial shown.
5. On failure: server detail or **Failed to remove photo**; clear busy state.

Photo actions are independent of unsaved Education/Account drafts. They do not save those drafts, require contact verification, or create a new account.

### Refresh and ambiguous results

The current web refreshUser logs/swallow errors; upload/remove can show success even if the follow-up user refresh failed. This is an observed limitation, not guaranteed UI consistency.

For mobile, reuse the existing profile/session state handling: merge the successful POST key or clear it after successful DELETE and reconcile against `/api/auth/me`. Preserve other user fields.

If a POST/DELETE response is lost, reconcile authoritative user and fresh image before claiming the mutation failed or automatically repeating it. With replacement, the same key cannot distinguish old/new bytes; a fresh authenticated GET is needed.

The backend's storage upload and database commit are not a cross-service atomic transaction. A storage write can precede a failed DB update, and the POST contains no explicit not-found error for a missing post-upload user lookup.

## 8. Copyable mobile request examples

These are integration templates using the mobile project's existing client and secure token retrieval, not new website code.

### React Native-style multipart example

The existing picker/cropper should produce a URI containing actual JPEG bytes.

```javascript
const origin = 'https://api.eduwai.in';
const token = await existingSession.getAccessToken();
const form = new FormData();
form.append('file', {
  uri: croppedJpegUri,
  name: 'photo.jpg',
  type: 'image/jpeg',
});

const response = await fetch(
  origin + '/api/student/profile/photo',
  {
    method: 'POST',
    headers: { Authorization: 'Bearer ' + token },
    body: form,
  },
);
if (!response.ok) {
  // Decode detail as string or structured 422 array.
  // Reuse existing session refresh/retry handling for 401.
  throw await existingApiError(response);
}
const result = await response.json();
// result: success + profile_photo_url logical key.
// Update/refresh user and invalidate/fetch private avatar cache.
```

Do not hardcode real tokens. Do not manually set multipart Content-Type in this fetch example. Merely renaming a HEIC file to photo.jpg or changing its MIME does not convert its bytes.

### HTTP/curl reference

Documentation only; these mutation commands were NOT executed.

```bash
# Upload OR replace. curl generates the multipart boundary.
curl -X POST 'https://api.eduwai.in/api/student/profile/photo' \
  -H 'Authorization: Bearer <access token>' \
  -F 'file=@photo.jpg;type=image/jpeg'

# Read current user's binary JPEG.
curl 'https://api.eduwai.in/api/student/profile/photo' \
  -H 'Authorization: Bearer <access token>' \
  --output current-avatar.jpg

# Remove photo, not account.
curl -X DELETE 'https://api.eduwai.in/api/student/profile/photo' \
  -H 'Authorization: Bearer <access token>'
```

## 9. Native acceptance checklist

1. Existing photo displays using an authenticated read, not the logical storage key as a public URL.
2. No-photo state displays the current user's initial or S.
3. Change Photo opens selection; no mutation until crop Save.
4. Cancel picker/crop leaves saved photo unchanged.
5. Crop uses 1:1 with round preview and zoom 1–3; output actual JPEG pixels.
6. JPEG/PNG/WebP files use the correct MIME; unsupported native formats are converted before submission or explicitly rejected.
7. Submitted file respects 5,242,880-byte limit; backend retains resize/compression ownership.
8. Initial upload and replacement both use POST with binary field file.
9. Stable-key replacement invalidates native cache so the new image is visible.
10. Busy state prevents duplicate selection, save, and remove operations.
11. Errors retain a retryable crop and do not claim a failed response undid a committed mutation.
12. Remove uses photo DELETE, not account DELETE; successful result clears display and Remove control.
13. Account refresh preserves other user fields and does not clear contact/education drafts or usage.
14. Avatar cache is scoped/cleared on logout and user change.
15. Failure to physically delete storage bytes is not represented as guaranteed erasure.
16. Native picker/crop permissions and lifecycle handling remain in the mobile project, not a new backend/web change.
